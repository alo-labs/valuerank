# ValueRank project instructions

## Required model inclusion

- Include every model represented on Artificial Analysis' Pareto frontier of Intelligence Index score versus the total USD cost to run the Intelligence Index benchmarks. Use total benchmark cost, not cost per task or token price.
- Include every near-frontier model family. A plotted configuration is near-frontier when its public (rounded integer) Intelligence Index is within 3 points of the rendered frontier's Intelligence Index at its cost, where the frontier's Index at cost c is the highest Index among rendered-frontier points costing no more than c. The family's selected configuration may differ from the near configuration. Defer a near-frontier family only by a dated, reasoned roster decision; report the cost ratio to the frontier for information only.
- Frontier membership is Artificial Analysis' rendered line as observed, never recomputed from rounded values.
- On 2026-10-23 the owner limited the cohort to the configurations AA plots on its rendered frontier or within 3 Index points of it, each plotted effort its own row (O51). The earlier retention of off-frontier configurations with exact DeepSWE and Bug Hunt results (O31, O33) is withdrawn; a near family ranks its plotted near configurations that have every leaf, and is otherwise listed under O38.
- Capture the complete selected catalog and retain exact model identities, reasoning efforts, observation dates, and direct owner links in the reconciliation inventory. Reconcile frontier entrants on each routine refresh; a manually maintained roster or missing supplementary benchmark must not silently exclude a frontier model. Classify every footnote the Intelligence Index chart capture records in data/aa/aa_footnote_register.json before the build (O100); from the next AA capture, also record and register the notes on model pages, the Coding Agent Index and the cost charts (O103).
- Preserve configuration-specific evidence. Do not transfer benchmark results between reasoning efforts or model versions. Report missing benchmark coverage explicitly and apply the documented scoring policy.
- On 2026-10-21 the owner decided that only configurations with the full benchmark set are ranked (O36). A required frontier or near-frontier family whose selected configuration still lacks a quality benchmark after an exhaustive search logged within 7 days of the release cutoff is listed with its missing benchmarks and the search, not ranked (O38). That logged exclusion is the only way a frontier family goes unranked; repeat the search on every refresh. A listed frontier or near-frontier family shows an indicative value on the leaves it has, apart from the ranking and labelled not ranked and not comparable (O41).

## Value scoring

- ValueRank ranks the AA Pareto and near-Pareto models by actual value, separately for API buyers and Plan (subscription) buyers. Methodology v3 (2026-10-19) is specified, with every owner and editor decision, in `research/2026-10-19-methodology-codesign/`; the published summary is `methodology.md`.
- On 2026-10-19 the owner set cost at a fixed 25% of the value score on both the API and Plan bases (`COST_WEIGHT_PCT` in `valuerank/plan_costs.py`); quality takes the other 75%. Missing quality evidence never changes cost's share, and a configuration without a cost gets no value score.
- Token efficiency is AA's published cost to run the SDLC cost basket for the exact configuration: the Intelligence Index's software-development evaluations plus the Coding Agent Index (v2.0 since 2026-10-23, owner decision O50: FrontierCode, Terminal-Bench and SWE-Atlas-QnA-AA; FrontierCode's cost is counted only inside it), each component admitted once its exact-configuration cost is captured for at least two-thirds of the cohort jointly with the other admitted components (owner decision O15; admission rule E140), counted within each ranking's own rows (owner decision O57, 2026-10-23); total Index cost is a diagnostic only. The clip gate counts ranked rows only; a listed configuration beyond a ranking's anchors never holds a release and is disclosed, a rendered-frontier point marked (owner decision O58, 2026-10-23). A configuration missing an admitted component is scored on its own subset of the basket and flagged (O17). Cost is scored on a log scale against frozen, versioned anchors, so cost ratios keep their magnitude and one model's entry never moves another's score. Every Coding Agent Index row AA lists is registered by AA's row id in a reviewed manifest, as the exact record of one cohort configuration or not; a new, relabelled or vanished row stops the next refresh until it is registered (owner decision O64, 2026-10-25). AA data read after the release cutoff is never merged into a pinned capture: it moves the cutoff, every AA source is re-captured and the anchors are re-frozen (owner decision O65, 2026-10-25). AA's published safety-refusal outcomes (attempts a refusal blocked, attempts a fallback model finished) are captured, published and flagged per row, but never change a cost, its completeness or a score (owner decision O63, 2026-10-25).
- On the Plan basis, cost is the basket's API cost divided by a subscription route's Value Multiple at full utilisation (O3). On 2026-10-23 the owner decided that the Plan ranking has one row per configuration and plan (O48): every plan with an eligible route for the configuration, the route on each plan chosen by the official comparator; a configuration with no eligible route keeps one API-cost row, flagged (O13). Routes whose multiple is not identified on the basket are scored and flagged (O16); routes past expiry fall back to API cost, flagged (O13). Every route record names exactly one model and one plan (O45).
- Quality is the weighted mean of the benchmark leaves for the exact configuration, each on fixed 0-100 anchors (software engineering 60%, general professional work 20%, reliability 10% as AA's Omniscience Index (O28), long context, science and knowledge 10%). On 2026-10-23 AA withdrew DeepSWE v1.1 and the owner dropped it in favour of FrontierCode (O49): software engineering is FrontierCode 1.1 25%, Terminal-Bench 4.0 20% and Bug Hunt Bench 15%, ten leaves in all. On 2026-10-23 the owner decided that ValueRank picks each ranking's benchmark set and ranks the configurations that have all of it (O52), and publishes two rankings (O53–O55): the max-effort ranking, shown first, adds Vals Vibe Code Bench v1.1 5 and Code Migration v1.1 6 and, by owner decision O61 (2026-10-23), LiveBench 2.0 Overall 15 (LiveBench's own Overall of its seven categories, all needed in the SDLC, from its 2026-10-23 release and weighted as that release weights them (owner decision O67, 2026-10-25); it replaced the Long Agentic and Coding categories, and as an uncontaminated benchmark it weighs no less than any single AA leaf: it ties FrontierCode, owner clarification 2026-10-23), with FrontierCode 15, Terminal-Bench 11 and Bug Hunt 8; the AI Coding Daily ranking adds AI Coding Daily without its bug-finding column 10 (FrontierCode 21, Terminal-Bench 17, Bug Hunt 12). Each ranking has its own anchors, bars and scenario run. Surge's Complex Constraints (dropped for now), CursorBench and Surge sudo L7 (excluded by the owner) and MirrorCode, SWE-bench-Live and SWE-PolyBench (too few exact configurations) are not used; MiMo-V2.6-Pro's results are taken at high, its AA configuration (O54), and Kimi K3.1 Pro's at max, its maximum and default effort (O66, 2026-10-25). Only configurations with every leaf of a ranking are ranked in it (O36). Every non-AA quality source is captured at most 30 days before the release cutoff (O59), and when the cutoff moves every board a ranking uses is re-read, a changed board in full (O68, 2026-10-25), and a capture taken after the cutoff stands only when the source's own last update is dated before the cutoff's day (O60), a board-level test; a row dated on the cutoff's day under it is disclosed (O69, 2026-10-25). The GDPval-AA leaf is the Elo AA's model page displays at each release's capture, not the value at a configuration's first capture, and a move between captures is disclosed (O70, 2026-10-25). A first-party plan of a frontier or near-frontier model's provider is valued from at least two actual user reports of its allowance, researched by plain web search, then Claude's Deep Research, then Silver Bullet's Deep Research (O71, 2026-10-25). Until two concordant user reports exist, the owner-authorised routes stay (SemiAnalysis with O40/O45, the O46 MiMo ceilings) and other providers' rows use API cost (O72, 2026-10-26); two concordant user reports replace only an assumption-based or fallback route, never an exact controlled measurement (O73), admission is the strict all-reports concordance test (O74), and every release runs all three research stages over every model and tier (O75). A speed-mode report is converted at the provider's published multiplier and flagged (O76); a provider's own announcement of a change to a plan's limits or price triggers change detection (O77, O101); and a concordant report pair dated after a detected change outranks the flagged controlled measurement (O78). A detected change to a meter several plans share flags every plan on it (O79), and a 5-hour figure stays in its own unit and never converts to a billing period (O80, O82). A provider announcement or a detected change to a plan's limits or price splits the report partition for the plans it covers and flags the routes on them, so earlier reports never count after it; a metering-only announcement is logged and does neither (O83, O99, O101); a change detected on any Kimi plan splits every Kimi plan (O84). Every report cell is tested; one on a plan the Plan ranking does not list is published as evidence only (O85). A controlled measurement taken inside an acknowledged accounting-fault window for its plan stays selected and flagged, with every route resting on it, until two concordant user reports for that plan and model replace it (O91, O92, O93). A lower-of transfer then re-takes the lower of its plan's effective figures (O95), and every other transfer or O88 route takes its own donor's replacing figure (O96). An O88 route that follows its donor to a report pair then takes the pair's "reports" grade and provenance (O97). Routes resting on a demoted donor measurement follow that model's admitted report pair on the same plan (O102). A lower-of transfer takes the lower of its plan's eligible figures, so a demoted measurement no pair replaced drops out (O104). A documented model-availability change flags a plan's routes without splitting its report partition (O105). A row whose AA cost AA says omits a pricing term competes over its published cost up to AA's stated factor, earns no label and is never an anchor reference from the next re-freeze (O94). Without a stated factor it competes over [C, ∞) (O98). AA chart footnotes are classified once in a register by exact text, and the build stops on any new or changed footnote (O100). Concordant means the largest lower bound is at most 1.20× the smallest upper bound (O86), and reports at any reasoning effort pool for the model, because an allowance is effort-invariant (O87). The build computes report admission from the report table (data/plan_reports.json) and refuses a report route no passing cell supports (O81, 2026-10-26). A leaf comes, in order, from AA (or the benchmark's own primary source), from another party that ran the same benchmark version on the exact configuration, then from the model provider's published result. Terminal-Bench is AA's own run, with tbench.ai filling gaps; FrontierCode is AA's, then Cognition's (O37). Nothing is transferred across efforts or versions, and there is no quality floor (O8). Interval outputs protect the published record (O25); scenario shares and diagnostics never change a score. A task-sampling stream approximates benchmark noise from each leaf's published task count, labelled as an independent-task approximation, and the ranking states how many adjacent ranks it separates (O39) and prints each row's noise band, the rank positions it cannot be told apart from (O42). Each quality bar's cheapest result has a companion at the bar plus the quality noise margin (O44), and the frontier and bar claims cover ranked configurations only (O43).

## Subscription allowance value-multiple evidence

- For providers other than the explicitly selected Anthropic/Codex SemiAnalysis comparison below, count only actual end-user-reported usage measurements priced at API rates as the value-multiple numerator. Accept the user's API-priced estimate as a reported estimate even when the raw token ledger is not published; label what cannot be independently reproduced.
- Never use a model provider's published allowance, quota, usage multiplier, or marketing estimate as the numerator. First-party information may establish subscription fees or API rate cards, but not the measured allowance value. Two owner exceptions: the MiMo quota ceilings (O46) and the conversion of a user's speed-mode report to standard-equivalent at the provider's published speed-mode multiplier, flagged (O76).
- Exception (owner decision O46, 2026-10-23): Xiaomi prices MiMo Token Plan credits at exact parity with its pay-as-you-go API, and no end-user measurement of a MiMo-V2.6 billing period existed after deep research. Each MiMo-V2.6 model therefore takes, per Token Plan tier, the quota-implied ceiling (the tier's monthly credits valued at Xiaomi's API rate for that model, divided by the list fee), labelled provider-derived and not a measurement; it replaced the earlier provisional 1.5x assumption. Replace a tier's ceiling with end-user measurements for the exact model and tier as soon as they meet the same admission rule as any other provider's route (O11); one report alone does not replace it (owner decision O62, 2026-10-23).
- Match reported API-priced usage to the exact model variant(s) the user says they used (the model, not the reasoning effort: an allowance is effort-invariant, O87, and a SemiAnalysis figure for a model serves every effort of it, O88). Keep mixed-model or unidentified use at provider/plan level; do not transfer it to a specific ValueRank model.
- Record the end user's plan tier and report date for every data point, plus the measurement window where stated. Use reports from the preceding month and exclude measurements that fall outside that window when the report isolates them.
- For Anthropic and Codex, use the latest SemiAnalysis analysis explicitly selected by the user on 2026-10-07: https://newsletter.semianalysis.com/p/anthropic-subscriptions-offer-5x. This authorization supersedes TiboTattle-only sourcing for the current Anthropic/Codex comparison. Label SemiAnalysis results as controlled subscription-account measurements with workload projections, not individual crowdsourced reports or provider claims. Preserve exact model, plan, workload, publication date and allocation regime. Historical TiboTattle data remain aggregates of installation/account tracks, not individual-user observations; do not mix them into current SemiAnalysis figures.
- On 2026-10-18 the owner authorized applying Opus 5.5's measured SemiAnalysis Claude plan multiples (Pro, Max 5x, Max 20x) to every other Claude model in the roster. Record those routes as user assumptions with the caution that allowances are model-specific (SemiAnalysis measured Fable 5.1 at 12.4-12.7x on the same plans), keep Opus 5.5 on its exact measured routes, and replace a shared route with an exact measurement for the listed model as soon as one exists, including one SemiAnalysis adds to the selected article after selection, labelled "added after selection"; other changes to that article stay diagnostic until the owner re-selects it (O40).
- The owner authorizes the same ChatGPT plan multiples for every GPT model. On 2026-10-23 the owner decided (O45) that GPT-6.1 Sol and GPT-6 Astra keep their own SemiAnalysis figures on every ChatGPT plan, bound to each model's unsuffixed (max) row because SemiAnalysis names the models without an effort; each of their other efforts takes its own model's figure per plan as a labelled same-model route (O88, 2026-10-28): measured evidence ranked just below an exact-effort measurement and above user reports, so every effort of a model has one multiple (O89, O90), and every other GPT model takes per plan the lower of the two reported figures as a labelled user assumption naming its donor route.
- A weekly scheduled task searches the web and SemiAnalysis's X accounts for a new SemiAnalysis subscription-usage analysis (owner instruction, 2026-10-22); a new article changes nothing until the owner selects it.
- Keep subscription fee evidence separate from allowance evidence. A provider's published price can be the denominator only when the reported tier and price mapping are supported.

## Subagents

- For work in this project, launch subagents with GPT-6.1 Sol at Medium reasoning effort (`model: gpt-6.1-sol`, `reasoning_effort: medium`). The user escalated from GPT-6 Luna Max to Sol Low; Sol Low's first 10 recorded assessments also averaged below 4.75, triggering the next effort level under the assessment policy. This preference applies only to ValueRank and must not be copied into global Codex instructions. Continue the assessment-based effort adjustment policy using actual completed-run scores.
- Give each subagent an explicit bounded scope, required inputs, deliverable, and file ownership where edits are involved. Tell agents to preserve changes made by others.
- Independently inspect and validate every completed subagent result against its sources, files, or execution evidence. Rework material deficits with the same required model and effort.
- After each completed subagent run, provide a concise user-facing micro-report naming the model and effort, task and result, independently verified evidence, defects or omissions, what remains unverified, and whether rework is needed.
- Maintain `subagent-model-scores.csv` at the ValueRank project root (this repository checkout) for this project only. Preserve existing rows; after each completed run is independently assessed, append a row with exactly five columns: `timestamp,model_slug,reasoning_effort,score,task_complexity`. Use an ISO 8601 UTC timestamp, exact model slug, actual effort in lowercase, an integer score from 0 to 5, and `low`, `medium`, `high` or `unknown` for the verified launch complexity. Record each follow-up or rework run separately. Do not invent historical scores or duplicate a run.
