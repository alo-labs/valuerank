# ValueRank project instructions

## Required model inclusion

- Include every model represented on Artificial Analysis' Pareto frontier of Intelligence Index score versus the total USD cost to run the Intelligence Index benchmarks. Use total benchmark cost, not cost per task or token price.
- Include every near-frontier model family. A plotted configuration is near-frontier when its public (rounded integer) Intelligence Index is within 3 points of the rendered frontier's Intelligence Index at its cost, where the frontier's Index at cost c is the highest Index among rendered-frontier points costing no more than c. The family's selected configuration may differ from the near configuration. Defer a near-frontier family only by a dated, reasoned roster decision; report the cost ratio to the frontier for information only.
- Frontier membership is Artificial Analysis' rendered line as observed, never recomputed from rounded values.
- Capture the complete selected catalog and retain exact model identities, reasoning efforts, observation dates, and direct owner links in the reconciliation inventory. Reconcile frontier entrants on each routine refresh; a manually maintained roster or missing supplementary benchmark must not silently exclude a frontier model.
- Preserve configuration-specific evidence. Do not transfer benchmark results between reasoning efforts or model versions. Report missing benchmark coverage explicitly and apply the documented scoring policy.
- On 2026-10-21 the owner decided that only configurations with the full benchmark set are ranked (O36). A required frontier or near-frontier family whose selected configuration still lacks a quality benchmark after an exhaustive search logged within 7 days of the release cutoff is listed with its missing benchmarks and the search, not ranked (O38). That logged exclusion is the only way a frontier family goes unranked; repeat the search on every refresh. A listed frontier or near-frontier family shows an indicative value on the leaves it has, apart from the ranking and labelled not ranked and not comparable (O41).

## Value scoring

- ValueRank ranks the AA Pareto and near-Pareto models by actual value, separately for API buyers and Plan (subscription) buyers. Methodology v3 (2026-10-19) is specified, with every owner and editor decision, in `research/2026-10-19-methodology-codesign/`; the published summary is `methodology.md`.
- On 2026-10-19 the owner set cost at a fixed 25% of the value score on both the API and Plan bases (`COST_WEIGHT_PCT` in `valuerank/plan_costs.py`); quality takes the other 75%. Missing quality evidence never changes cost's share, and a configuration without a cost gets no value score.
- Token efficiency is AA's published cost to run the SDLC cost basket for the exact configuration: the Intelligence Index's software-development evaluations plus the Coding Agent Index, each component admitted once its exact-configuration cost is captured for at least two-thirds of the cohort jointly with the other admitted components (owner decision O15; admission rule E140); total Index cost is a diagnostic only. A configuration missing an admitted component is scored on its own subset of the basket and flagged (O17). Cost is scored on a log scale against frozen, versioned anchors, so cost ratios keep their magnitude and one model's entry never moves another's score.
- On the Plan basis, cost is the basket's API cost divided by the selected subscription route's Value Multiple at full utilisation (O3). Routes whose multiple is not identified on the basket are scored and flagged (O16); routes past expiry fall back to API cost, flagged (O13).
- Quality is the weighted mean of the eleven benchmark leaves for the exact configuration, each on fixed 0-100 anchors (software engineering 60%, general professional work 20%, reliability 10% as AA's Omniscience Index (O28), long context, science and knowledge 10%). Only configurations with all eleven are ranked (O36). A leaf comes, in order, from AA (or the benchmark's own primary source), from another party that ran the same benchmark version on the exact configuration, then from the model provider's published result. Terminal-Bench is AA's own run, with tbench.ai filling gaps; FrontierCode is AA's, then Cognition's (O37). Nothing is transferred across efforts or versions, and there is no quality floor (O8). Interval outputs protect the published record (O25); scenario shares and diagnostics never change a score. A task-sampling stream approximates benchmark noise from each leaf's published task count, labelled as an independent-task approximation, and the ranking states how many adjacent ranks it separates (O39) and prints each row's noise band, the rank positions it cannot be told apart from (O42). Each quality bar's cheapest result has a companion at the bar plus the quality noise margin (O44), and the frontier and bar claims cover ranked configurations only (O43).

- For work in this project, launch subagents with GPT-6.1 Sol at Medium reasoning effort (`model: gpt-6.1-sol`, `reasoning_effort: medium`). The user escalated from GPT-6 Luna Max to Sol Low; Sol Low's first 10 recorded assessments also averaged below 4.75, triggering the next effort level under the assessment policy. This preference applies only to ValueRank and must not be copied into global Codex instructions. Continue the assessment-based effort adjustment policy using actual completed-run scores.

- Independently inspect and validate every completed subagent result against its sources, files, or execution evidence. Rework material deficits with the same required model and effort.
- After each completed subagent run, provide a concise user-facing micro-report naming the model and effort, task and result, independently verified evidence, defects or omissions, what remains unverified, and whether rework is needed.
- Maintain `subagent-model-scores.csv` at the ValueRank project root (this repository checkout) for this project only. Preserve existing rows; after each completed run is independently assessed, append a row with exactly five columns: `timestamp,model_slug,reasoning_effort,score,task_complexity`. Use an ISO 8601 UTC timestamp, exact model slug, actual effort in lowercase, an integer score from 0 to 5, and `low`, `medium`, `high` or `unknown` for the verified launch complexity. Record each follow-up or rework run separately. Do not invent historical scores or duplicate a run.
