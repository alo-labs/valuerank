M1 — Two coexisting, differently-defined noise margins beside the same bar answers. O44's companion uses 1.96 × √2 × the median row SD; O171's pointwise screen uses per-pair √(σ_i² + σ_H²) with a frozen setter SD. A bar answer can carry a displayed margin of, say, 3.6 points (median) while its own σ_answer makes the true pair margin far off that figure, and readers have no rule for which number speaks. This is a new argument over O128: O128 rejected a per-candidate margin *before O171 existed* (2026-10-30 vs 2026-11-03); the O171 screen is the per-comparison construct O128 lacked, and it is strictly more accurate for the displayed-record answer. Recommendation: retire the O44 median companion where the O171 screen panel exists, or re-derive the companion from the screen (margin_i = 1.96·√(σ_answer² + σ_H²) per answer), keeping O44's median only as the spacing flag's input where it is actually a population object.

M2 — E268 couples two quality leaves to one selection primitive. AI Coding Daily's record is chosen by matching its harness to the Bug Hunt record's harness, so any Bug Hunt harness switch (new largest-sample run, or an E224 tie resolved by a reason) silently moves the AI Coding Daily leaf too. E334 attributes the two effects separately in the replay, but the ranking downstream still consumes the leaves as independent: O42's noise-band correlation grid is over benchmark draws, not over selection events, so a shared harness-selection shock hits two leaves of the same row jointly with no correlation treatment. Recommendation: register each model's AI Coding Daily harness by its own fixed policy (e.g., the AA-matched vendor CLI, falling back to a named default), decoupled from Bug Hunt record selection; keep E224's alternates publication; publish an E309-style ±1 sensitivity on the pair only if the policies ever coincide.

M3 — Bug Hunt's S1T kernel is an unboundedly conservative dispersion for a multi-run mean. E326 reads planted fixes as a single-run binomial plus the unplanted count as a Poisson count, deliberately not divided by run count "since repeated runs share their tasks and repositories." But the owner's published per-run values exist (E29 notes they are captured and unused by any v1 stream), and runs sharing fixed tasks is precisely the setting where the run is the correct resampling unit: a run-level bootstrap over the owner's published run means quantifies the between-run component without pretending tasks were redrawn, exactly as the workload cross-check already does a "model-row bootstrap." The current kernel inflates Bug Hunt's contribution to every separability threshold and noise margin, biasing all labels conservative by an unknown factor. Recommendation: add a named Bug Hunt stream σ² = between-run bootstrap variance (of the multi-run mean, over the owner's N published runs) + planted-task binomial at the Jeffreys proportion, published beside the E326 single-run envelope; restate thresholds under the pair as E309 does for covariance.
