Bug Hunt live-scale denominator has a one-way ratchet and a cross-harness unit (Owner decision challenge, O170/O173). The scale z = 100·x/(P_max + U_max) takes its maxima over "every run on the live board, any model or harness", recomputed every release. Two new arguments beyond the settled ±10% stress: (1) P_max and U_max are order statistics whose expected values grow with the number of published runs, so the scale drifts downward as board activity accumulates, correlated with how many runs providers publish rather than with any ranked model's performance — the published stress is symmetric while this drift is one-directional and unbounded across releases; (2) the denominator can be set by a harness the numerator never uses, while the leaf's stated estimand is model+harness (E29), so the normalising constant is not on the leaf's own measurement object. This hurts the objective because an 8–15% quality share in both rankings moves with no new evidence about any ranked row. Concrete change: derive P_max and U_max within the harness family of each row's selected record (per-harness scales), or freeze the scale per anchor version and let the a-version bridge carry changes; extend bugHuntScaleStress with the observed historical drift of the two maxima across the last k releases so readers see the ratchet's realised magnitude.

The drift flag cannot see a collapsing leaf it excludes (E114). A leaf with cohort SD(z) below 3 points is marked non-discriminating and excluded from B*, and the drift flag's D_g is renormalised over the same B* — so the exact event the flag exists to detect (a group's discriminating share collapsing under its nominal weight) is removed from the flag's population, leaving only the non-discriminating tag. Combined with the O170 scale, Bug Hunt compression would leave the software-engineering group's nominal 60% weight intact while its discriminating share fell, silently diluting every other leaf's effective influence. Concrete change: publish an "effective discriminating weight" per group (Σw_b over leaves with SD ≥ 3, alongside the existing normalised weighted spread) and raise a named flag whenever a leaf carrying ≥ 8% of quality turns non-discriminating.

The AI Coding Daily leaf is selected by Bug Hunt's run-count arithmetic (E268 + E206). The AICD record is the row whose harness matches the configuration's Bug Hunt record, and E206's largest-sample rule means that record can switch harness when more runs accumulate on another CLI — switching the AICD row with no new AICD evidence. E334 and O162 attribute and flag this after the fact, but nothing measures how close each selection is to flipping, so a release can carry a changed 10% leaf whose cause is invisible until the E177 replay runs. Concrete change: publish a flip threshold per affected row (the run count on the alternate harness that would switch the selected record) beside the existing alternates, and a one-row sensitivity showing the AICD leaf under harness-independent selection (latest test date), so the coupling's cost is visible each release.

2. Methodology design recommendations

Prioritised, all implementable from refreshed public data:

Harness-consistent or version-frozen Bug Hunt scale. Either z_i = 100·x_i/(P_max^{h(i)} + U_max^{h(i)}) with h(i) the harness family of row i's selected record, or the current whole-board maxima frozen per anchor version with the a-version bridge carrying the change. Add bugHuntScale.maximaDrift (the two maxima's values over the last k releases) to the existing stress output.

Effective discriminating weight beside the drift flag. For each group g, publish Σ_{b∈g, SD(z_b)≥3} w_b and the same sum over all leaves, plus a named flag when a leaf with w_b ≥ 8% turns non-discriminating. No score change; pure diagnostic in the E114 output block.

AICD flip threshold and decoupled-selection sensitivity. For each row selected under E268, compute how many additional runs on the alternate harness would switch the Bug Hunt largest-sample record, and the AICD leaf value under latest-test-date selection. Publish beside alternates in data/swe_tracks.json provenance.

Leaf-description registry check. Add the source's own stated task counts (and question counts) per leaf to the registry, and have the build compare the draft's leaf-table descriptions against it — this automates catching the Code Migration count class of error at every refresh.

Off-anchor listed-row summary. Extend the O58 disclosure with a per-release summary (count by side, median factor, count past the factor-2 limit, per basis), so the routine pattern visible in part 9 — many listed Plan rows 4×–70× below the low anchor — becomes trendable rather than a flat list.
