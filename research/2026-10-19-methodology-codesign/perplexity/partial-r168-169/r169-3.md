## 1. Findings by severity

**Critical**

None.

**High**

1. **The Plan measurement base is entirely flagged at this release, and the draft never states the aggregate consequence.** Part 5/6 record that every SemiAnalysis route — i.e. every controlled measurement, the entire authorised route set — is change-flagged (Claude shared-meter change typed unclear → open-ended hull; OpenAI price change of 2026-10-11), and that the staged searches found **no** cell with two concordant end-user reports, so the O78 repair path is unreachable at this release. Each route's flag is published individually, but no roll-up tells a reader that zero Plan rows rest on unflagged measured evidence. This hurts the objective (a defensible public value ranking) because the systemic condition — the whole Plan ranking rides on one flagged source plus labelled assumptions and provider-derived ceilings — is reconstructable only by cross-reading per-row fields. The external record corroborates the fragility: independent measurement of Ultra after this cutoff lands near $6,801/month of API value versus SemiAnalysis's $11,726 (agentic) and $9,385 (A/B arm B), and SemiAnalysis's own A/B arm moves monthly value ~20% between same-day accounts. Recommended change: publish a per-release `planEvidenceHealth` table — Plan rows by evidence grade × flag type × hull status — plus one sentence in the Plan output ("N of M ranked Plan rows rest on unflagged measured routes"; today N = 0). All inputs already exist in `planRows`. [wokey](https://wokey.ai/claude-usage-limits)

2. **O198 tier-priced routes are scored at the short-context tier with a disclosed but unbounded optimism of up to 5×.** Part 6 states Claude Haiku 5.5's long-context tier prices every token category five times higher (GPT-6 Luna 1.5–2×), so "a long request divides those two routes' multiples by up to that factor and their Plan rows are optimistic for long requests by that much." A 5× multiple error dwarfs every precision instrument the methodology maintains elsewhere (±20% concordance, the 1.20 band, O115 clipping), so these rows' Plan value scores are not comparable to other rows at the ranking's stated precision. Both inputs for a fix are public: OpenCode publishes per-model dollar limits measured at its token prices, and the basket's demand region is already captured. Recommended change: for each tier-priced O198 route publish a bracket \(M_{short} = L/p_{short}\), \(M_{demand} = L / \sum_d w_d p_d\) (weights \(w_d\) from the basket demand projection), \(M_{long} = L/p_{long}\), and run at least one scenario arm at \(M_{demand}\). The published record stays at the current figure under O25. [sessionwatcher](https://sessionwatcher.com/guides/opencode-pricing)

**Medium**

1. **The E124 mix-unmatched flag (L1 > 0.30) has no quantified downstream effect.** It is "shown, not silently trusted," but nothing converts the mismatch into a number a reader can weigh against the Plan value score, and the E210 category-mix bound is inactive (no cache split). Recommended change: a scenario arm for mix-unmatched routes that scales the multiple by the ratio of demand-projection-weighted to measurement-mix-weighted effective price over the categories the source reports, disclosed as unbounded where the cache categories make it so.

2. **Comparator key 3 selects the maximum observed multiple among unidentified candidates with no representation of the induced selection bias.** Picking the max of k noisy observations systematically overstates the Plan multiple (winner's curse). E171/E179 publish the alternative table and leave-selected-out choice, which discloses the gain but does not correct the bias, and O25 confines noise to scenario shares — where this bias is currently absent. Recommended change: a scenario arm that draws such rows at the geometric mean of their unidentified candidates, and print (k, max/median gap) beside each row selected on the max.

3. **The SemiAnalysis re-read (O130) records the read but, as stated, does not hash or archive the fetched bytes.** End-user reports must carry a SHA-256 archived copy under O165/O124, yet the single most load-bearing evidence source — the only controlled measurements, not captured in the evidence bundle at all — has a weaker provenance standard. A changed figure is currently detectable only against the selection-time transcription. Recommended change: store each re-read's fetched bytes (or their SHA-256 plus the quoted figure table) in `sourceEvidence.semianalysis.rereads`, matching the O165 standard.

4. **Single-source risk with no calibration check.** O35 correctly removed the Fable donor-error gauge, but nothing replaced it: O11 admits "a controlled saturation measurement with receipts (e.g. SemiAnalysis …)" — the "e.g." is never exercised — and the ±20% tolerance machinery applies only to end-user reports. Public evidence now shows independent saturation measurements diverging from SemiAnalysis by ~20–45%  and ~20% account-level variance inside SemiAnalysis's own A/B arms. Recommended change: operationalise a controlled-measurement intake (receipts + archived copy, O124-style) so a second observer can qualify under O11 as written, and publish a one-plan-per-release cross-check of the selected figure against any independent controlled measurement as a calibration diagnostic. This adds a source rather than loosening any gate. [wokey](https://wokey.ai/claude-usage-limits)

## 2. Methodology design recommendations

Prioritised; all are computable from data the build already captures or from public pages.

1. **`planEvidenceHealth` roll-up (High 1).** Each release: a matrix of ranked Plan rows × {controlled measurement, report pair, owner assumption, quota ceiling, published limit, API fallback} × {unflagged, flagged–direction known, flagged–unclear (open hull)} × {point-identified, set-identified, unidentified}, plus the headline sentence. Data source: `scores.json planRows` and the registry's change records. Normalisation: none needed (counts). Uncertainty handling: none needed beyond the hull status column.
2. **Tier bracket for O198 routes (High 2).** \(M_{short} = L/p_{short}\), \(M_{demand} = L/\sum_d w_d p_{d}\), \(M_{long} = L/p_{long}\), where \(L\) is the published dollar limit, \(p_d\) the tier prices, \(w_d\) the basket demand projection. Publish all three; keep \(M_{short}\) as the published record (O25); run one scenario arm at \(M_{demand}\) and label the row's tier exposure. [sessionwatcher](https://sessionwatcher.com/guides/opencode-pricing)
3. **Mix-sensitivity scenario arm (Medium 1).** For mix-unmatched routes with reported shares, an arm scaling the multiple by \(\frac{\sum_d w_d \tilde p_d}{\sum_d x_d \tilde p_d}\) over the reported categories (\(\tilde p\) a common per-category reference price), disclosed unbounded where cache categories dominate.
4. **Selection-bias arm (Medium 2).** For rows selected on the max of k ≥ 2 unidentified candidates, a scenario arm at the candidates' geometric mean, with (k, max/median) printed — the alternative table already holds the inputs.
5. **Archive the O130 re-read (Medium 3).** SHA-256 of fetched bytes per re-read in `sourceEvidence.semianalysis.rereads`.
6. **Second-source qualification path (Medium 4).** A "controlled measurement" intake channel with receipts, archived copy, allocation regime (E220) and observation date (E194), admitted under O11 exactly as written; plus a standing calibration diagnostic whenever two controlled measurements exist for one route.
7. **Basis sensitivity pair for OpenCode prices (Low 2).** Publish DeepSeek at off-peak and Gemini undiscounted as labelled sensitivities with the basis-matching rationale stated.
