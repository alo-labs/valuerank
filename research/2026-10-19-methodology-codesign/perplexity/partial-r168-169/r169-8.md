## 1. Findings by severity

**Critical**

None.

**High**

None.

**Medium**

1. **The O198 OpenCode dollar-limit multiple has no rate-consistency condition.** The draft states OpenCode's published dollar limit is its actual limit, with "multiple = limit / fee, no staged search", and justifies it as a hard cap rather than a marketing quota. But the Plan numerator convention stated in this same part (and in O46's MiMo ceilings, which deliberately value "credits at the API rate") is **API-priced consumption**. A dollar cap binds on the seller's own metered rate r_m per token, not on the API list price p used for valuation. If r_m ≠ p, the API-equivalent consumption the cap enables is L·(p/r_m), so the correct multiple is (limit × p / r_m) ÷ fee, and limit/fee misstates it by the rate ratio. Why it hurts: OpenCode Go routes are admitted and scored (O203, O199), so a rate mismatch would be a first-order bias in a scored Plan quantity, with the "provider-derived" flag giving no bound on the bias. Recommended change: add a build check that records the route's metered price basis and the valuation price basis; where they are not the identical price list, publish the converted multiple (with the ratio disclosed, mirroring O46's structure) or flag the ceiling with the rate-ratio band as a structural bound on M_W. Add a release-test fixture (metered rate at 1.25× API rate → multiple scales by 0.8). This specifies the owner's exception rather than challenging it.

2. **E62(a) quality agreement confounds evidence substitution with weight change, and only the confounded statistic is published.** Part 17 defines Q_ind as the *unweighted* mean z of the independently executed leaves while the observed composite is weighted, and the parenthetical concedes that "(a) too changes the evidence and the relative leaf weights together". As published, the τ_b cannot tell the reader whether disagreement comes from the independent evidence or from the switch to equal weights — which is exactly the question the check exists to answer. Recommended change: publish a second, matched-weights variant alongside: Q_ind^w = Σ_j w_j z_j ÷ Σ_j w_j over the independent leaves j, with w_j the composite's own relative weights renormalized over that subset, and run the same τ_b against the observed composite. Two τ_b values (matched and equal-weight) bracket the evidence effect. Purely computational, refreshes every release, no new data.

3. **LINUX DO is read only through a mirror, although a direct automated fetch is available and would strengthen the O11/O71 evidence base.** The known-limitations section discloses that the staged search reads LINUX DO — "where many end-user reports for Kimi, Xiaomi and MiniMax plans are posted" — only via a mirror, and that a "no concordant pair" outcome for those providers partly reflects search reach. LINUX DO is a Discourse instance, and Discourse exposes documented public JSON endpoints (e.g. `/posts.json`, `/search/query.json`, topic endpoints) that return structured data without an approval process. Reddit, by contrast, is structurally unreachable: unauthenticated `.json` requests have returned 403 since May 2026, and Reddit stopped accepting new public Data API access requests after October 31, 2026, so the indexed mirror remains the right automated approach there. Why it hurts: report-pair concordance is the binding constraint on Plan evidence for exactly the providers whose reports live on LINUX DO, and mirror staleness or incompleteness can produce false "no concordant pair" outcomes that route those plans to API fallback. Recommended change: add a direct Discourse JSON fetch as an automated stage for LINUX DO (same E223 independence typing, hashed artifacts under O124/E165, reached/unreached logged), keeping the mirror only as a fallback. This does not challenge O197 — it is *more* automation, not an owner-run manual pass. [docs.discourse](https://docs.discourse.org/)

**Low**

1. **Scenario draws remain Python-version-fragile when a portable design is cheap.** The draft correctly notes that Python guarantees only that `random()` itself reproduces across versions, not the Beta and normal samplers built on it — the standard library documentation states exactly this guarantee for the generator's `random()` method under a compatible seeder  — and mitigates by recording the drawing Python version and treating a version change as a change of draw order. Recommended change: implement the non-uniform kernels in-repo as documented inverse-CDF (or rejection) transforms consuming only `random()` uniforms, making every scenario file reproducible across Python versions; keep the recorded version as defence in depth and keep the existing fixture that a version change is read as a draw-order change. [docs.python](https://docs.python.org/3/library/random.html)

2. **The E62 checks print no power statement, and today they are always low-powered.** Part 17 reports leave-AA-out as "not identifiable" (34% and 22% independent quality weight) and reads the disjoint-evidence check as low-powered below 40% — meaning every current panel is in the low-power regime. Recommended change: beside each τ_b, publish the bootstrap CI half-width and a minimum detectable |τ_b| (the smallest effect the panel's configuration count could distinguish at the declared level), so "low-powered" is quantified and a reader can see what the check can and cannot rule out.

3. **The capacity LP has no solver-independence check.** Part 15 publishes feasible_lower_bound and relaxed_upper_bound (a solver-independent bracket — good), but the certified point capacity requires the bounds to coincide, and a degenerate LP can admit multiple optimal vertex schedules across solvers. Recommended change: record the solver identity and version beside each capacity result, and add a release fixture running the same capacity problem through a second solver, asserting objective agreement within tolerance (vertex schedules may differ; the bracket must not).

## 2. Methodology design recommendations

Prioritised:

1. **Rate-consistency condition for quota-ceiling numerators (implements Medium 1).** Per route with a provider-derived ceiling, store `metered_price_basis` and `valuation_price_basis` as price-record IDs; multiple = (limit × p_API ÷ r_metered) ÷ fee when the bases differ, disclosed beside O46's existing structure; build fails if either basis is unrecorded. Refreshes with the existing price-record machinery (E141, E170).

2. **Matched-weights independent-evidence check (implements Medium 2).** Q_ind^w = Σ_j w_j z_j ÷ Σ_j w_j over independent leaves; τ_b against both the observed composite and the value recomputation of E62(b); publish matched and equal-weight τ_b side by side with the same cluster bootstrap (E329). No new evidence needed.

3. **Direct LINUX DO Discourse stage (implements Medium 3).** Scheduled fetch of `/posts.json` and `/search/query.json` filtered to the plan tags/keywords already used in the staged search; same report typing (O99 record types), same independence test, hashed artifacts; the registry's search log gains a "direct" reach marker beside "mirror".

4. **Version-proof scenario kernels (implements Low 1).** In-repo inverse-CDF samplers on `random()`; each scenario file keeps `generator`, seed and Python version; a fixture asserts a draw under two Python versions yields identical files.

5. **Power disclosure for E62 (implements Low 2).** CI half-width and minimum detectable |τ_b| beside every published τ_b, with "undefined" carried through the existing panel-too-small convention.

6. **Cross-solver capacity fixture (implements Low 3).** Second solver on the release-test capacity fixtures; assert bracket coincidence is solver-independent.
