## 1. Findings by severity

**Medium**

1. **Basket-component completeness is gated by non-basket evaluations' arithmetic (E209/O175, part 3).** CompleteCostEvidence for the six Index SDLC evaluations requires that "AA's nine evaluation costs reproduce its published Index total within the O175 materiality band" — but three of those nine (Omniscience, HLE-Diamond, CritPt v2) are not basket components and carry no quality leaf. A data quirk in a knowledge benchmark's per-evaluation cost (Omniscience at 3,000 tasks is the likeliest residual carrier) can flip a coding row's six perfectly-published SDLC costs to "unresolved", stripping its FullCost status, interval eligibility, R_W/P_K membership and anchor eligibility, without anything being wrong with the costs the ranking actually prices. This hurts the objective because the value ranking's cost basis and its eligibility machinery diverge on evidence the ranking does not use. The current Opus residual (0.03–0.04%) sits safely inside the band, but nothing in the design localizes or isolates residuals to non-basket components. **Recommendation:** (a) where AA publishes per-evaluation figures for the three non-basket evaluations, attribute any residual to its evaluation by cross-capture differencing before applying the unresolved status, and exempt the six basket components when the residual is fully attributed to a non-basket evaluation; (b) where attribution is impossible, publish a bounded sensitivity that charges the residual to the dearest basket component (at today's magnitudes, ≤0.04% of C_W, i.e. demonstrably immaterial) so the conservative gate is visibly cost-free rather than silently strict.

2. **Owner decision challenge (O24, part 3): the Terminal-Bench family's priced multiplicity is unquantified.** Terminal-Bench 4.0 is priced twice by design (Index run + vendor-agent run inside the pooled Coding Agent Index), and Terminal-Bench-Science adds 70 more terminal tasks, so the terminal-task family carries a large and *uncomputable* effective weight in the max-effort basket — the CAI's TB share is not separable from its one pooled cost. The published disclosures (E200 coding share with/without TB-Science, E343) aggregate across families but never state the basket's task-family composition, and the effective TB weight differs between the two rankings (index admitted vs pending), so the label "SDLC cost basket" implies a workload mix that is never printed. This weakens the objective's cost-25% story: a reader cannot tell how terminal-heavy the priced workload is, and the double-priced execution inflates terminal weight relative to any real buyer's SDLC mix. **Recommendation:** publish, per workload version, a task-family composition table (task counts and cost share by family: FrontierCode, TB-4.0 Index run, TB-4.0 CAI run (equal-cost-assumption, labelled, as already used for the 77%/224-of-290 figure), TB-Science, AutomationBench, Briefcase, GDP.pdf, SWE-Atlas QnA), with the double-counted TB execution shown as its own line. This is implementable entirely from data already captured and does not change O24 itself.

3. **The Index-reconciliation procedure is not reproducible from the text (part 3, "Accounting identities").** The paragraph first states the total "decomposes into its **nine** v5 evaluations (Σ cost per task × task counts: …)" with task counts for all nine, then says locating the Opus excess "would need a per-evaluation total beyond the **six** component costs AA lists". It is left ambiguous whether AA publishes per-evaluation cost figures for all nine evaluations or only for the six SDLC ones, and how the reconstruction is computed for the three non-basket evaluations. A fresh implementer (or a future refresh after AA changes its page fields) cannot rebuild the E209 check from this text alone, which hurts refreshability — a stated requirement of the objective. **Recommendation:** one sentence in the accounting-identities bullet naming the exact AA fields used per evaluation (and, for the three non-basket evaluations, whether the figure is published or derived), registered in the cost-evidence registry alongside the boundary records.

## 2. Methodology design recommendations

Prioritised, all implementable from public data captured in the routine refresh:

1. **Task-family composition table per workload version (highest priority).** For each ranking's W, publish task counts and basket cost share by execution family, with the CAI's internal split (FrontierCode 1.1, SWE-Atlas QnA, TB 4.0) shown under the labelled equal-cost assumption already established for the 77% figure, and the two priced TB executions on separate lines. Data source: the existing component costs, task counts already quoted (91/657/100/132/66/70 and the CAI's 100/124/66), and `diagnostics.basketReadiness`. This turns the O24 overlap and the E203 unrewarded share into a single readable workload-mix statement and lets readers judge the 16–74% CAI-share spread's effect on comparability.

2. **Residual-localization protocol for O175 rows.** For any row whose nine-way reconstruction misses (today: the three Claude Opus 5.5 rows), diff the per-evaluation cost figures between the two most recent AA captures and publish the per-evaluation deltas beside `indexReconciliation`. If AA publishes all nine figures (see Medium 3), this attributes the residual directly; if only six, the deltas bound where it cannot be. Either way the "cause stays unregistered" state becomes an evidence state, not an open-ended one, and re-reading at every release (already promised) gets a concrete procedure.

3. **Non-basket decoupling bound (pairs with Medium 1).** Publish, next to the E209 status scale, the worst-case C_W perturbation from any in-band residual, computed as the residual charged to the row's largest basket component: today max 0.04%, i.e. below the cost noise the scenario layer already carries. This documents that the conservative nine-way gate cannot move a rank, converting a structural strictness into a quantified no-op until AA's data breaks the band.

4. **Fallback-price capture rule (pairs with Low 1).** Mirror E176/E216 for `data/fallback_prices.json`: capture date ≤ 7 days before V, per-model provenance, a build check that a price change in a named fallback model re-captures, and the sensitivity's two ends flagged when any input price is older than the release.

5. **Missing-telemetry ceiling from attempt coverage (E53).** The registry already publishes attempt coverage (telemetry-covered vs required attempts). Reusing the equal-cost-per-attempt assumption already adopted for O158's fallback share, publish a per-row scenario-layer ceiling C × (required / covered) for rows with coverage below 100%. This gives the O25 "cost precision" language a concrete, assumption-consistent number, and requires only fields already captured.
