## 1. Findings by severity

**Critical**

None.

**High**

- **Owner decision challenge (O87, new argument): cross-effort report pooling is internally inconsistent with O146.** The draft's rationale for pooling reports across efforts is that "a plan's allowance is the same dollars at any effort" (O87). The new argument, not in the ledger: the draft itself refutes this premise two pages later. O146 says a plan meter counts tokens (O126), so a measurement at one effort is rescaled by *r* = the configuration's own Intelligence Index price per token over the donor effort's — i.e., the draft recognises that a fixed token allowance is worth different API dollars at different efforts, because the reasoning/output mix changes the effective $-per-token. If that difference is large enough to bracket for controlled O88 same-model routes, the identical effect cannot be treated as zero for report routes, where a low-effort observer's pooled cell value "support[s] a route of any configuration of that model" with no bracket at all. Why it hurts the objective: the Value Multiple numerator is API-priced consumption; a value rooted in a wrong-effort mix is silently wrong in exactly the direction O146 already quantifies for other routes, and consumers of the comparison see one displayed number. Concrete change: when a report route is displayed for a configuration whose effort mix differs from the pooled evidence's, publish the O146 bracket mechanism beside the cell value (same formula, same `planRouteBrackets` sensitivity pattern), mirroring O181 — point kept, bracket beside. This is latent today ("the end-user report routes (none)") but becomes binding the first time a report cell admits.

**Medium**

- **O76's single published speed-mode multiplier misses OpenAI's funding-source split.** OpenAI documents Fast mode consumption at 2.5× standard on subscription allowances but **2× standard on purchased credits and Enterprise metered usage**, and ChatGPT credit multipliers do not apply when billing via API keys. The draft's O76 converts every speed-mode reading at one multiplier ("OpenAI Fast 2.5×, Ultrafast 8×"). Because part 7's quota schema itself mandates non-overlapping funding flows (subscription entitlement, bundled credits, purchased usage — E54), a report that mixed subscription allowance with purchased-credit consumption converted at 2.5× would be misstated by up to 25% on the purchased portion. Concrete change: make the speed-mode conversion read the report's recorded funding basis and apply the published multiplier per flow; where the basis is unrecorded, admit only if the observer's wording bounds it, else exclude — consistent with the existing `windowStated`-style provenance test. (The 2.5×-only conversion is correct for pure in-plan allowance readings, so this is a refinement, not a reversal.) [learn.chatgpt](https://learn.chatgpt.com/docs/agent-configuration/speed.md)
- **O144 cross-model transfer brackets span the weakest source of uncertainty.** The Claude transfer bracket uses the shared-mix list-price ratio (plus per-category ratios), while the dominant quantity — each model's own effective API price per metered token, set by its own reasoning/cache mix — is computable from data the draft already holds: E124 records per-configuration cost per task, output tokens per task, and Index-wide category totals, and part 8's E131 verifies per-configuration token identities (e.g., output = answer + reasoning for GPT-6 Astra xhigh). O146 already uses exactly this own-units formula for cross-effort routes. Concrete change: add an own-mix headline bracket \( r_{\mathrm{own}} = (p \cdot \bar{d}^{(\mathrm{target})}/T_{\mathrm{target}}) \div (p \cdot \bar{d}^{(\mathrm{donor})}/T_{\mathrm{donor}}) \) from category totals to every O144 transfer, keeping the shared-mix and per-category brackets as documented sub-cases; a category with no positive donor price leaves the component bracket unavailable, per the existing rule.

**Low**

- **52/12 weekly conversion is a long-run average, not any subscriber's attainable figure.** For calendar-reset weekly windows a 30-31-day billing period contains 4 or 5 weekly resets (≈ −7.7%/+15.4% around 4.333), while session-anchored windows average ≈4.35. The draft discloses the convention, and under O3 full utilisation the average is defensible; recommend publishing the attainable-range sensitivity (4 vs 5 resets) for plans whose recorded window semantics are calendar/fixed reset, using the quota schema's existing semantics field. [atlasbudgeting](https://www.atlasbudgeting.com/subscription-cost-calculator)
- **O46 ceilings value redeemed credits against the list fee**, but Xiaomi publishes a 12% first-purchase discount and 12% annual auto-renew discount on the same tiers. A new subscriber's actual gross cash is lower, raising the realised ceiling. Recommend the route record state its fee basis (steady-state list fee) explicitly, so readers don't read the ceiling as the purchaser's actual multiple — consistent with the ceiling's existing "optimistic end on use" flag. [platform.xiaomimimo](https://platform.xiaomimimo.com/token-plan)
- **Two-observer cells carry no robustness annotation.** Where exactly the minimum concordant pair decides a cell's value, publish the leave-one-observer-out range beside `bandMoved`; it is computable from the `readings` list the registry already keeps and makes the fragility of a two-report route visible without changing admission.

## 2. Methodology design recommendations

1. **Unify the bracket machinery into one formula across route classes** (highest priority). Define each route's transport ratio as \( r = (p \cdot m_{\mathrm{target}}/T_{\mathrm{target}}) \div (p \cdot m_{\mathrm{donor}}/T_{\mathrm{donor}}) \) where `m`, `T` come from the cheapest available evidence of the consuming entity's own mix, in precedence: (a) the entity's own E124 category totals, (b) the registry's shared mix. Apply uniformly to O144 transfers, O146 routes (already), and report routes when effort differs (Section 1 High). This removes the current three ad hoc bracket definitions while preserving O181's displayed-point policy and would have prevented the O87/O146 asymmetry structurally.
2. **Funding-basis-aware speed-mode conversion in `plan_reports.json`.** Add `fundingBasis ∈ {allowance, purchased_credits, unknown}` per report; convert each flow at its published multiplier (2.5× allowance / 2× purchased for Fast ); reject admission when the basis is `unknown` for a speed-mode reading. One schema field, one build check — fits the existing admission data flow (O81). [learn.chatgpt](https://learn.chatgpt.com/docs/agent-configuration/speed.md)
3. **Per-category-effort bracket for pooled report cells.** Publish, per passing cell, the min/max effective price-per-token ratio across the efforts the cell supports (from category totals), as `effortBracket`, so a reader sees how much of a cell's spread is mix-induced versus allowance-induced — the decomposition the bracket sections currently only hint at.
4. **Window-semantics-attainability sensitivity.** Extend quota-schema outputs so every weekly-window route carries `resetsPerPeriod ∈ [4, 5]` (calendar reset) or `4.333` (session-anchored) alongside the converted multiple; zero effect on displayed values, removes a recurring reviewer question.
5. **Cell-pooling robustness diagnostics.** Publish per-cell leave-one-observer-out value range and the observer count behind every admitted route directly in `planAllowanceCells`, so route strength is visible without reading the research record.
