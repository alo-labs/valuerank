LiveBench 2.0 Overall kernel lacks the dual reading its twin leaf gets. The S1T kernel takes the seven categories' counts as "Long Agentic 18, Reasoning 4, Coding 29, Browser 25, Data Analysis 3, Research 22, Design 25", with Reasoning and Data Analysis counting parts "so their counts are the wide reading" (E264). AI Coding Daily gets exactly the same problem — published count versus independent-unit count — and gets a published narrow companion (n = 6 beside n = 60, E263); LiveBench Overall gets none, despite carrying 15 points and tying FrontierCode as the largest max-effort leaf (O61). Counting parts where a task holds several short questions inflates effective n and shrinks the SD in 2 of 7 categories, so the "dispersion stress" is least stressful precisely where the count is weakest as an independence unit — this feeds the separability statements, noise bands and the O171 noise margin. There is also a terminology trap: for AI Coding Daily "wide reading" means the wider-variance reading (n = 6), while for LiveBench "wide reading" means the wider count (narrower variance); a reader mapping "wide" consistently will misread one of the two. Recommended change: publish a task-level (or effective-n) companion beside each LiveBench separability figure, mirroring E263, and rename the readings by dispersion direction (e.g. "count-narrow"/"count-wide") so the labels cannot be cross-mapped.

Bug Hunt noise-model constants are not bound to the live board. The leaf's SD formula embeds "105 planted bugs" and the board maxima P_max + U_max as fixed inputs, while O170/O173 make the scale live each release and E343 anticipates Bug Hunt version aliases. E346 froze the maxima as exact release constants, but the planted count inside the SD formula is a board property, not a rounding constant; nothing in these parts names a rule that re-reads it when the board changes. After a board change the noise band, the separability statement and the O171 noise margin would be computed on a stale n, silently mis-sized — and O173's ±10% stress only brackets the scale, not the count. Recommended change: extend the build-check pattern (as E216/E217/E225 do for captures) so the kernel's planted count, P_max and U_max are re-derived from the live board capture each release and the build fails on a mismatch with the registered kernel object; a mismatch caught mid-cycle can be published as a named swing class under O173.

GDPval-AA ratings are drawn independently while pairwise ordering shares are headline outputs. The draft discloses that a fitted Crowd-BT model's ratings covary through shared matchups and that pairwise differences may be over- or under-dispersed, and leaves it "disclosed, not corrected" — yet E96 publishes f_ij win/tie/loss frequencies as per-stratum scenario outputs, which is exactly where this covariance bites. Bug Hunt's correlated counts got a −1/0/+1 bracket (E309); GDPval-AA got none for the same problem class. Recommended change: a named GDPval correlation bracket — recompute the pairwise series under a common-factor draw (every row's rating shifted within its displayed interval by one shared draw) and an opposed draw, published beside the primary series, analogous to E309. It is implementable entirely from the already-captured per-row intervals and changes no score.

Owner decision challenge (O182/O183): the like-for-like gate is partly self-referential. The gate compares basket cost — which contains the Terminal-Bench component — against Terminal-Bench cost per attempted task; the draft itself concedes "a pass shows agreement with that component", with the leave-one-component-out τ_b printed beside it as the broader reading. Today's numbers show the stakes: AI Coding Daily reads τ_b 0.35 on cost per solved task against 0.91 on the inclusive like-for-like check, so its labels stand on a pass the shared component helps produce. The new argument is that the non-circular statistic already exists — it is computed for attribution — so gating on the leave-one-component-out reading (or withholding when either reading falls below 0.5) costs nothing and removes the self-reference from the label decision. Why it hurts: the cheapest-above-bar label is the headline claim; a pass driven by the shared component can issue labels in a ranking whose broader basket ordering disagrees with execution-level cost efficiency.
