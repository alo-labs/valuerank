## 1. Findings by severity

**Critical**

None.

**High**

1. **Owner decision challenge (O24): duplicate terminal-task pricing is a weight distortion, and AA's index evolution is about to generalize it.** Part 3 prices Terminal-Bench 4.0 twice in the same basket (the AA Index run and inside the CAI's pooled cost) and Terminal-Bench-Science is a third terminal execution, while the quality side credits terminal work only through the Terminal-Bench leaf (11 of 100 points in the max-effort weighting, O55). The "each is what a user of that deployment pays" rationale answers why each number is real, not why one SDLC basket should contain two passes over the same 66 tasks: a user runs them once, so the basket systematically over-weights terminal-execution spend relative to its quality weight, penalizing models that are expensive on terminal tasks relative to their quality there. This is disclosed as "overlap," but it is a score-shaping issue, not just a transparency one. The new argument: AA has since moved the Coding Agent Index to v2.1, whose components are FrontierCode-AA 2.0 (132 tasks) and Terminal-Bench 4.1  — i.e., the same benchmark and task count as the basket's separate "FrontierCode 2.0 (AA Index run, 132 tasks)" unit. Part 3's invariant "the two components never price the same tasks" holds for v2.0 but breaks at the next capture, extending the duplicate-pricing problem from Terminal-Bench to FrontierCode. **Recommendation:** pre-commit a collision rule before the v2.1 re-capture — when a CAI-internal benchmark's task set intersects a basket unit's, either retire the lower-evidenced unit for that ranking (the O17/O184 subset machinery already supports it) or keep both under O24 but publish, beside the E200 coding share, a leave-one-unit-out sensitivity (drop the Index TB 4.0 unit; separately drop the CAI unit) using the existing E172/E149 objects, labelled "duplicate-execution bound." Implementable from public data; no score change is required to publish the sensitivity. [artificialanalysis](https://artificialanalysis.ai/agents/coding-agents)

2. **The agent-cost confound is disclosed but invisible at the headline layer and has no activation trigger.** Under O123/O200 the CAI's agent-mediated token spend (16–74% of basket cost in the max-effort ranking, per part 3) is charged to the configuration while quality leaves come from AA's bare-model runs, and the S2 stress (log C = α_m + h_a) is explicitly unevaluable while no model is listed under two agents. AA's own methodology frames its comparisons as "like-for-like agent variants within the published benchmark suite", which underlines that agent identity is a real cost axis, and independent commentary notes harness choice carrying much of the measured differences. Today a reader of the published tables cannot see which agent a row ran under or its CAI share — both live only in scores.json (`rows[].codingAgent`) — so a value ranking can partly rank agents without the reader knowing. **Recommendation:** (a) print the coding agent and CAI cost share per row in the published tables (not only scores.json); (b) print each ranking's agent mix (rows per agent); (c) add a build trigger that runs S2 automatically the moment AA lists any cohort model under two agents, so the confound is quantified at the first opportunity rather than waiting for a review cycle. As an owner decision challenge to O200: labels earned by rows whose CAI share is majority and whose agent differs from the panel's modal agent rest on an unidentified deployment effect; the minimum-cost fix is (a)–(c), not withholding labels. [artificialanalysis](https://artificialanalysis.ai/methodology/coding-agents-benchmarking)

**Medium**

3. **The CAI cost is re-priced at live cache-hit rates, and the boundary record does not say so.** Part 3's E158 boundary says AA prices provider-reported token counts (basis not published per configuration; metering mix printed), and O27 calls the ×290 figure "the published record of one deployment-equivalent pass (E9)." But AA's coding-agent methodology states that when reporting cost it combines token counts "with live measurements of the model's typical cache hit rate, rather than relying on the one-off measurement when the evaluation was run". So the published CAI cost is a current-price model of a pass, not the realized spend of the captured run: it can move between captures with no new run, and it is cache-modeled at typical rates rather than the run's realized cache behaviour. E176 registers cache-rate provenance and treats cache-rate updates as bridge causes, but the boundary text for the CAI unit should carry this explicitly, since it also calibrates what the O158 fallback re-pricing's price-ratio ends mean. **Recommendation:** add one provenance line to the CAI unit's boundary record: "priced at live typical cache-hit rates (AA methodology), re-valued at each capture; not the run's realized spend," and note it beside the O27 metric statement. [artificialanalysis](https://artificialanalysis.ai/methodology/coding-agents-benchmarking)

4. **E214's silent-fallback match default has no empirical check.** Part 3 matches a third-party record silent on fallback "by model and effort, whichever way AA plots the model," and only explicitly mismatched records are excluded. Fallback state is treated as material everywhere else in E214 (the build fails on AA's own with/without contradiction), yet the silent default assumes it does not matter for that benchmark's score, untested. **Recommendation:** publish a fallback-state sensitivity diagnostic: where both an AA-plotted run and a silent-matched third-party record exist for the same model and effort, print the value difference; flag rows whose leaves were gap-filled by silent-matched records on models AA plots with fallback. Implementable from data the build already captures.

## 2. Methodology design recommendations

Prioritised:

1. **Pre-commit a task-overlap collision rule for the CAI vs Index units** (addresses High 1). Concrete design: at each refresh, compute the intersection of the CAI's internal benchmark set (from AA's methodology page and index version history ) with the basket units' benchmark-task sets; if non-empty, publish a `duplicateExecution` flag per affected unit pair and a leave-one-unit-out run of the value score and ranks (E172/E149 object per unit, anchor object unchanged, labelled sensitivity-only). This is fully automatable from AA's published index composition and the existing accounting tree. [artificialanalysis](https://artificialanalysis.ai/agents/coding-agents)

2. **Surface the agent axis in the published layer** (addresses High 2). Concrete design: add two columns to each ranking table — `codingAgent` and `caiShare` (A_i / C_i) — plus one summary line per ranking with rows per agent; add a build-time predicate `anyModelUnderTwoAgents` that, when true, evaluates S2 (log C = α_m + h_a, centred within connected groups) and publishes the agent-adjusted API ranks beside the main ranking. All inputs already exist in the manifest (O64) and scores.json; this is a presentation and trigger change, not a methodology change.

3. **Extend the E158 boundary record with a pricing-time field** (addresses Medium 3). One enum per component: `run-realized`, `live-re-priced` (cache rates), `mixed/unknown`, sourced from AA's methodology page at each capture. This makes the "costs move without re-runs" behaviour legible and feeds the E176 bridge-cause machinery.

4. **A fallback-state concordance diagnostic** (addresses Medium 4). For every (model, effort) with both an AA-plotted leaf value and a silent-matched third-party value on the same benchmark, publish the signed difference and a per-benchmark median; if the median exceeds the O44 noise margin (4.5 points today), the build flags the silent-match default for that benchmark as suspect rather than silently continuing to admit silent records.
