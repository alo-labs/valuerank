## 1. Findings by severity

**High**

None. The cost-anchor machinery (E253/E160/O157/E184/E304), the clip gate (E312, O58, E262), the re-freeze and dual-run paths (O47, O65, O68, O132, O120), the leaf table arithmetic (weights sum to 100 per ranking; the coding-specific shares, source shares of 66/34 and 78/22, the doubling-offset figures 3.11/4.14, 5.31/7.08, 2.71/3.61, 4.11/5.48, and the Omniscience non-monotonicity example 82 vs 66 all check out arithmetically) are internally consistent in these parts.

**Medium**

1. **"Independent" source-share label covers first-party evidence.** The quality source-share diagnostic classifies leaves as AA-run vs "independent, meaning executed by a party other than AA (Bug Hunt, the two Vals boards and LiveBench 2.0 Overall)" (part 10), yet E206 selects Bug Hunt records from "the owner's published results" and "the owner's run notes", and the roster/scoreboard are ValueRank bundle artifacts (O31) — i.e., Bug Hunt appears to be executed by ValueRank itself, not a third party. Why it hurts: the published "34% independent" invites readers to read third-party validation of a third of quality weight; for a public ranking whose credibility rests on provenance, overstating independence is a real integrity exposure even though the definition is printed inline. Change: split the diagnostic three ways — AA-run / owner-run / third-party — and footnote Bug Hunt's provenance wherever the leaf appears; if Bug Hunt is in fact third-party, the question in Section 3 settles it and this finding closes.

2. **AI Coding Daily harness selection is coupled to the Bug Hunt harness with no sensitivity output.** E268 selects the AICD row whose harness equals the configuration's Bug-Hunt-record harness, so "a Bug Hunt refresh that changes the selected harness can change this leaf too although no AI Coding Daily row changed" (part 10); the replay attributes it (E334), but the size of the swing is never published, and no cross-harness agreement diagnostic exists for AICD even though duplicate rows are published as `alternates` (DeepSeek V4.1 Flash 1017 has DeepSeek Harness and OpenCode rows). Why it hurts: harness is one of the largest variance drivers in agentic coding boards, AICD carries 10–12% of its ranking's quality, and the coupling induces correlated selection between two leaves of the same row that S1T treats as independent — so a published rank can move on another board's run count, and readers cannot see by how much. Change: keep E268's deterministic rule, but for every row with `alternates` publish the row's value and rank computed under each matching harness row, plus a mean offset (and τ_b where the dual-harness panel is large enough), exactly as E224 and E229 already do for Bug Hunt and Terminal-Bench.

3. **Plan anchor references must be plan rows of API-side reference configurations (Owner decision challenge, O157).** O157 defines Plan references as "the plan rows of the same configurations whose displayed Plan cost is measured", i.e., a Plan reference must also be an API reference with complete cost evidence on every component. Why it hurts: measured plan rows are the scarcest evidence in the methodology; tying their anchor eligibility to API-side completeness can leave the Plan basis "unavailable" (or force an O193 API-only migration) for reasons unrelated to Plan evidence quality, cutting coverage of one of the two buyer bases the objective serves. Change: decouple eligibility — define Plan references as measured plan rows of cohort configurations with complete Plan-basis evidence (≥2), independent of API-side status, keeping E304's atomic migration and the two-per-base minimum.

**Low**

1. **One-sided LiveBench task-count bracket.** The S1T LiveBench SD keeps 2026-10-14 task counts and brackets only the halved-count end (SD × √2) (part 10). New argument beyond reviewers 96/111 (who settled that it is a sensitivity, not a bound): adding the doubled-count end (SD ÷ √2) closes the grow direction — the direction in which current separability statements are conservative — so published noise claims can be as strong as the evidence allows rather than only as weak. Cost: one extra number per release.

2. **AICD rater variance is unmodelled.** S1T's AICD unit is the six graded projects, and "the board publishes no error" (part 10); judged scores carry rater variance on top of project sampling. Change: label the AICD S1T term "project sampling only; rater variance unmodelled" beside the existing assumption label, and record in the registry whether the board publishes judge or per-project detail.

3. **Basis-dependent cost sensitivity is not surfaced at the headline.** A cost doubling is worth 3.11 value points on the max-effort API basis but 5.31 on its Plan basis (part 9), so the nominal "cost 25%" (E196) implies materially different cost sensitivities per basis. Change: print the per-basis value-points-per-doubling beside each ranking's headline, not only in the scoring section.

4. **Anchor workload-hash aliasing.** "The hash covers the workload's component set only … equal hashes imply no comparability across rankings" (part 9). A downstream user joining anchor objects on this hash will silently merge non-comparable objects. Change: rename it (e.g., `workloadShapeHash`) or fold ranking and basis into the hash input as a bridged anchor-version change.

## 2. Methodology design recommendations

Prioritised:

1. **Three-way provenance split in the source-share diagnostic** (fixes Medium 1): publish AA-run / owner-run / third-party shares per ranking from the existing provenance fields; no new data collection.
2. **AICD harness sensitivity** (fixes Medium 2): per row with alternates, publish value and rank under each matching harness row from `data/swe_tracks.json`; report the between-harness mean offset over the dual-row panel. Deterministic, refreshable, mirrors E224/E229.
3. **Leave-one-reference-out anchor sensitivity**: for each anchor object (especially the Plan bases, whose measured reference panels are small), recompute c_L, c_H, all cost scores, values and ranks excluding each reference in turn; publish the maximum delta. This is the anchor analogue of E172's leave-one-component-out cost family and directly quantifies how fragile each basis's cost scale is to a single reference — currently invisible.
4. **Decouple Plan reference eligibility from API-side completeness** (Medium 3, owner decision challenge): Plan references = measured plan rows of cohort configurations with complete Plan-basis evidence, ≥2; E304's atomic-migration and both-bases minimum unchanged.
5. **Two-sided LiveBench count bracket**: publish SD at halved and doubled counts; primary reading unchanged.
6. **Headline footnote with per-basis doubling cost** and the **hash renaming** (Low 3, Low 4).
