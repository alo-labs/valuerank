## 1. Findings by severity

**Critical**

None.

**High**

None. I verified the two load-bearing formulas in these parts and they are correct as stated: the E335/E23 repricing multiplier \((p'·u / p·u)(p·x / p'·x)\), and the E185 current-tariff Plan bound \(P' \in [P·\min r / \max r,\; P·\max r / \min r]\), which is the exact range of \((u\text{-weighted mean of } r) / (x\text{-weighted mean of } r)\) over unknown demand and consumption mixes (the narrower-looking \([P/\max r, P/\min r]\) would be wrong here precisely because \(u\) and \(x\) can differ). The O69 "N hours ago" bound (age > N−1 under rounding, truncation or ceiling) also checks out.

**Medium**

1. **Pass-independence in the capacity LP is the one untested assumption in the "only governing Plan formula."** The λ computation assumes every workload pass consumes the identical vector \(d_k\). Real subscription sessions have cross-pass effects the draft never stress-brackets: agent context/memory carryover across passes within a session, throttling-induced behavioural change (users report quotas tightening in effect even when the published cap is unchanged), and cache warm-up. Since the Plan headline (O3, full-utilisation Value Multiple) *is* \(M = \lambda \times C_{i,W}/F_{gross}\), a systematic per-pass drift ε scales effective consumption by roughly \((1+\varepsilon)\) at the binding budget, biasing the Plan cost basis with no disclosed uncertainty — while every neighbouring assumption (burst feasibility, monotonicity, repricing, split invariance) has a fixture. **Recommended change:** add a named sensitivity where pass \(j\) consumes \((1+\delta_j)d_k\) with \(\delta\) at published deterministic endpoints (e.g. ±10%) or drawn in the scenario stream; recompute λ with cumulative budget consumption and publish the induced movement in M and in adjacent rank order; sensitivity-only under O19; plus a release fixture asserting λ is unchanged when the drift model is disabled. This is implementable from the same public inputs the solver already uses.

2. **Scoped change detection has a stale-mirror gap.** E18 monitors named sections (pricing tables, rate-limit documentation, model-availability matrices) and treats a section that moves, is renamed or disappears as a change. But a provider that publishes new quota terms on a *new* page while leaving the monitored page in place, un-updated, produces "no change" — the monitored section never disappears. The backstops (≥2 independent end-user reports, O77 announcements) catch this late and only if users notice. This hurts the objective because Plan numerators rest on measurements representing the *current* quota regime; an undetected quota cut leaves a route scored as current, corrupting the Plan ranking's cost basis between backstop firings. **Recommended change:** publish the monitored-section registry (URL set, last-checked instant per provider) in the evidence bundle, and add a monthly automated re-derivation step — follow the provider's sitemap/navigation to locate the current pricing and rate-limit pages; a newly located URL differing from the monitored set is itself a typed change record under O99. Fully automated and refreshable, consistent with O197.

**Low**

1. **Scenario RNG is version-fragile by design choice.** The draft correctly notes Python guarantees only `random()` across versions and records the drawing Python version; community evidence confirms derived samplers have changed across versions while `random()` did not, and the official docs guarantee only `random()`'s sequence stability across Python versions. The current mitigation (record version; treat a version change as a draw-order change) discloses the problem but guarantees scenario shares lose cross-release comparability on any toolchain upgrade. **Recommended change:** implement every sampler (Beta, normal, binomial) as documented transforms of `random.random()` alone (e.g. Box–Muller, Marsaglia–Tsang), or pin a generator with a cross-version guarantee, and version the sampler itself; then a Python upgrade no longer reads as a redraw. [stackoverflow](https://stackoverflow.com/questions/8786084/reproducibility-of-python-pseudo-random-numbers-across-systems-and-versions)

2. **Grid resolution has no rule tying it to the shortest recorded window.** E39's default 15-minute grid cannot represent a quota window shorter than the grid (a per-5-minute cap would be silently unschedulable). Today's real windows are far coarser — Claude plans use session-anchored 5-hour windows plus weekly caps with account-assigned fixed resets  — so nothing current breaks. **Recommended change:** a build check that `grid_resolution ≤` the smallest window length among the route's recorded budgets, else the budget is marked unmodelable and the conservative bound applies with `semantics_status unresolved`. [support.claude](https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work)

3. **Mirror lag for unreachable report venues is disclosed but not measured.** The staged search cannot reach Reddit, X or YouTube directly and reads LINUX DO only through a mirror; the draft honestly notes that "no concordant pair" partly reflects where the search could look. **Recommended change:** a monthly automated mirror-freshness metric (latest reachable post timestamp vs. any reachable index of the source) recorded in the search log, so a "no concordant pair" outcome can be read against known mirror lag. Automated, public, no manual stage.

## 2. Methodology design recommendations

Prioritized; all implementable from public data refreshable at the monthly cadence.

1. **Per-pass consumption-drift sensitivity for the Plan capacity solver** (Medium 1). Formula: for binding budget \(w\), replace \(\lambda_w = B_w / \Sigma_k a_{wk} d_k\) with \(\lambda_w(\delta) = \max\{n : \Sigma_{j=1}^{n} \Sigma_k a_{wk}(1+\delta_j) d_k \le B_w\}\), \(\delta_j \in \{-0.10, 0, +0.10\}\) as deterministic endpoints (and optionally drawn in the scenario stream). Publish \(\lambda(\delta)\), \(M(\delta)\), and the rank movements between endpoints beside the capacity result; never into Θ or labels (O19). Add the disabled-drift fixture to the release tests.

2. **Monitored-section registry with automated re-derivation** (Medium 2). Per provider: monitored URL set, section selectors, last-checked instant, and a monthly sitemap/navigation crawl whose output diffs against the registry; any newly located authoritative pricing/quota URL is a typed change record (O99) even when the old page is unchanged. The registry entry appears in the E63 active-rules manifest.

3. **Version-stable sampler layer** (Low 1). Either (a) derive all non-uniform samplers from `random.random()` with documented transforms and a sampler version field in `scenarios.generator`, or (b) pin `numpy.random.Generator(PCG64)` with the sampler methods used, which carries a stable bit-generator contract. This removes the Python-version coupling that currently forces "a version change is read like a change of draw order."

4. **Grid-resolution guard** (Low 2): a build-time assertion, plus `grid_resolution` published per capacity result (already required by E56) cross-checked against the smallest recorded window.

5. **Mirror-freshness metric** (Low 3): one registry field per unreachable venue, updated by the monthly search itself.

Checked with no change needed (recorded for convergence): the E185 Plan bound and E335 multiplier (see High); the O69 age bound; the E30/E115 treatment of session-anchored vs fixed-reset windows, which correctly mirrors how real plans encode them — session windows starting at first use with full reset five hours later, and weekly limits resetting at fixed, account-assigned times.
