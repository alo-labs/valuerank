**Medium**

**M1. The scenario panel of a ranking that has subset-workload rows is not specified, the build leaves those rows out of every scenario table, and nothing published says so.**
- Where: Output 1 (lines 22–23) promises "Uncertainty is shown beside each rank as per-stratum scenario shares". E96 (lines 557–559) says each series has "a declared panel I … named with its size" and that "frequencies on different workload objects keep the label 'cross-workload ordering not identified' (O17)". E190 (lines 209–211) publishes subset-workload outputs for the frontier and bar interval outputs only. No sentence says which rows enter the scenario panel when a ranking has rows on a subset workload (today the max-effort ranking: DeepSeek V4.1 Flash 1017 (max) and MiMo-V2.6-Pro).
- What the build does: `value_v3.scenario_panel` (line 2534) keeps only rows whose cost is on the ranking's main workload. In the max-effort ranking the API panel therefore has 7 rows, not 9; the Plan S0 panel 22, not 27; the transfers-off Plan panels 12 (`scores.json` `v3.scenarios.results.*.panelSize`). `scores.md` "API basis: rank 1" lists seven configurations with GPT-6.1 Sol at 100%, while README.md's headline sentence (line 13) names MiMo-V2.6-Pro the API leader (rank 1, "subset cost") and its table gives DeepSeek rank 3. Neither `scores.md`, `methodology.md` nor the draft says that these two rows have no scenario share, or that "rank 1" in a scenario table means rank 1 among the seven main-workload rows.
- Why it hurts: line 559 reads as if panels may mix workload objects (a faithful implementer could put the subset rows in each panel on their own anchors with the O17 label); the build is a second reading; a third implementer could run the scenario engine on W_S, which covers all nine rows (E190). The three publish different rank-1, top-3 and frontier frequencies, including for the row the table shows first. A reader sees "Sol 100% rank 1" next to "MiMo-V2.6-Pro rank 1" with no explanation, and the "uncertainty beside each rank" statement is not met for two of nine rows. No score or label changes (scenario shares never do), which is why this is Medium and not High.
- Recommended change: state in E96 and in Output 1 that a ranking's scenario panel is its main-workload rows and that rows on a subset workload are outside it, listed with that reason (their uncertainty is their noise band and the E190 interval outputs). Have the emitter print each series' panel size and its excluded rows above the scenario tables, as it already does for the transfers-off exclusions. If the owner or editor prefers the other reading, say instead that subset rows enter the panel on their own anchors with the O17 label, and change the build to match. Either way the rule and the published tables should agree.

**M2. The O46 quota-ceiling rows are left out of the transfers-off rule as written, but the build treats them as transfers.**
- Where: E167 (lines 542–544: "a row whose pair is an owner-named transfer is unevaluable in the transfers-off streams (S1 core, S2 core and S1M)"), the Θ rule (lines 614–615: "a Plan route that depends entirely on an owner-authorised transfer is 'unevaluable'") and the release test (line 800) name only the owner-named transfer. The Assumptions bullet (line 324) lists two different things, "the owner-named model-to-model transfers … and the owner's MiMo quota ceilings (O46)", so by the draft's own vocabulary a ceiling is not a transfer. The draft does group them elsewhere when it means both: line 29 ("an owner-named transfer or the O46 quota ceiling"), line 368 and the † mark (E242). The E106 admission table (lines 330–335) has no case for a ceiling (case 2 is "owner-named transfer", cases 3–4 are measurements), so it is also silent.
- What the build does: `value_v3.transfer_dependent` (line 2512) is true for every route graded "assumption", and the MiMo ceiling routes carry `valueMultipleKind: user_assumption`. In the AI Coding Daily ranking, where MiMo-V2.6-Pro is on the main workload, its four Token Plan rows are among the 48 rows dropped from every transfers-off Plan panel, leaving a two-row panel (DeepSeek V4.1 Flash 1017 (max), Gemini 4 Argon (high)) (`scores.json` `v3Tracks.aicd.scenarios`; `scores.md` prints scenario tables for the leading ranking only). For the leading ranking the emitter already prints each dropped row as "depend on a transfer", and would print the MiMo ceiling rows the same way.
- Why it hurts: a literal reading of E167 keeps the four MiMo rows in the transfers-off panels, which gives a six-row panel and different Plan scenario shares in S1, S2, S1M and S1T (the max-effort ranking is unaffected today only because of M1). This is the same pattern the ledger rated Medium at I35 M1 (a rule general in the build, stated for one member of the class in the draft). The effect is confined to exploratory Plan shares, which never change a score or a label.
- Recommended change: define once, in the Assumptions bullet, "assumption-grade route = owner-named transfer or O46 quota ceiling (every route the comparator grades 'assumption')", and use that term in E167, the Θ rule, the line-800 release test, E242's † and the Output 1 count. Add the ceiling to E106 as case 2 (display-eligible only through its labelled assumption path, never identifies M_W, clock from the capture of Xiaomi's pages).

## 2. Methodology design recommendations

Priority order; all small and implementable from existing data.

1. Declare the scenario panel (M1). One sentence in E96 saying a ranking's scenario series range over its main-workload rows, an emitter line above each scenario table giving the panel size and the excluded rows with the reason, and a sentence in the README next to the leader line. If the owner would rather have shares for the subset leader, the lower-cost route is to admit subset rows to the panel on their own anchors with the O17 label, which is what line 559 already suggests.
2. Name the class once (M2). Introduce "assumption-grade route" for transfers and O46 ceilings, and have E167, the Θ rule, E242, E106, the Output 1 count and the release test cite it. The build already uses one test (`grade == "assumption"`), so this is a wording change.
3. Remove duplicated rule text that can drift. The MiMo paragraph of `methodology.md` is generated from `plan_cost_routes.json`, and the draft's line 328 and lines 367–368 say the same thing in two places. Keep one sentence per rule and let the others cite it; this is what produced L1 and L4.
4. Make a transfers-off Plan panel say when it is not informative. In the AI Coding Daily ranking the only rows left are the two with no Plan route at all (API-cost fallbacks), so its S1, S2, S1M and S1T Plan "rank 1" shares compare two fallback rows. A one-line rule would help: when a transfers-off Plan panel contains no row on a measured route, publish the streams as "not informative: no measured route" rather than as shares. This is a presentation choice; no score depends on it.
5. Extend the E265 lint (L5) to bare cohort family names in "today" sentences, and generate the "missing leaves today" and "report route" sentences from `leaf_evidence.json` and `plan_cost_routes.json`.
6. Print "Family (effort)" in every table, including the bare-name row (L2), and have the uniqueness check run on those names.
7. Not repeating: the ladder rungs that are closer than the noise margin (I44, I45) and the subset-cost headline label (I45 L4) are already recorded for the owner report. I add only that the first is more visible than the ledger says: the max-effort headline and upper bars are 0.75 points apart against a 3.8-point margin.
