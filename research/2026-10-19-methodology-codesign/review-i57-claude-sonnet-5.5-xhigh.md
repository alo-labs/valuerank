### Medium

**M1. The Coding Agent Index capture is not part of the routine refresh and has no clock, so the draft's "each refresh lists AA's new rows" and O64's "stops the next refresh" are not what the pipeline does.** The draft says (Cost, manifest): "The build stops when a captured row is not registered, … so each refresh lists AA's new rows and a release builds only after an editor has classified each." AGENTS.md says a new, relabelled or vanished row "stops the next refresh until it is registered". The stop is real, but it runs on the captured file, and three facts mean nothing makes that file current:

1. `npm run refresh` is `refresh:external && build:aa && build:scores && reconcile:aa && build:publication`. The Coding Agent Index and cost-chart captures are `npm run capture:basket` (`python3 -m valuerank.capture_coding_agents && node scripts/capture-aa-cost-charts.js`), which no other script, `docs/refresh-and-release.md` or `.github/workflows/*` calls. The refresh procedure lists `refresh:external`, `capture:deepswe` and `build:aa` as the automated captures and does not name `capture:basket`. The analogous stop for tbench.ai agents (E225) does fire in the routine refresh because `capture:tb4` is in `refresh:external`; the manifest's stop does not, so a refresh that nobody preceded with `capture:basket` builds on last release's rows without any message. A row that AA adds, relabels or removes after the last capture is exactly the case O64 exists for, and it is invisible until someone runs a command the procedure never mentions.
2. The draft's freshness regime lists every other AA artifact and the non-AA sources: model-page snapshot at most 45 days and price records at most 7 days (E216), chart and catalog capture at most 7 days (E211), chart and model pages at most 7 days apart "so a frontier point and the leaf values and costs it is scored with describe one AA state" (E217), non-AA quality sources at most 30 days (O59, O60). It names neither the Coding Agent Index capture nor the cost-chart capture. The build matches: `assemble` checks `snapshot`, `priceRecords`, `source_clocks` and the chart-to-snapshot gap only. I replaced `documents["codingAgents"]["capturedAt"]` and `documents["costCharts"]["capturedAt"]` with 2026-03-01 and ran `assemble` for the max-effort ranking at the 2026-10-23 cutoff: it builds, admits the Coding Agent Index and scores 9 rows with no message.
3. The Coding Agent Index is the largest priced component of the max-effort ranking (8 of 9 rows) and, with O64's manifest, the one component whose completeness the owner has just made a closed-world matter. Its freshness is the one thing the closed world cannot supply.

Two faithful implementers read the draft differently here: one adds `capture:basket` to the refresh and an age gate, the other builds on whatever file is on disk. This is the I39 M1 class (a scored artifact with no capture clock), and the new text makes the gap visible by promising a refresh-time guarantee that the pipeline does not give. No score changes today (the capture is 4 minutes after the chart). Recommended change: (a) put `capture:basket` in `refresh` before `build:scores` and in `docs/refresh-and-release.md`; (b) add the Coding Agent Index and cost-chart captures to the E216/E217 text and to `assemble` with the chart's 7-day limit (and the E217 gap to the chart); (c) say in the manifest sentence that the stop acts on the capture the refresh has just taken, so the sentence is true by construction.

## 2. Methodology design recommendations

1. **Make the refresh the place where O64 bites (priority 1, M1).** Move the Coding Agent Index and cost-chart capture into `npm run refresh` before `build:scores`, name it in the procedure, and gate both captures (and the safety read) by age: at most 7 days at the release cutoff and at most 7 days from the chart and from each other (E217's "one AA state"). The manifest check then acts on a capture the same refresh has taken, which is what AGENTS.md promises.
2. **Close the capture's row filter (L1).** Fail the capture when the payload holds more `displayLabel` objects than rows kept, and list the dropped ones with the reason; the manifest then registers every row AA lists, as the draft says.
3. **Pin O63's fields and state the flag (L2, L3).** Add the three AA fields, the sum over evaluations, the flag condition, the three statuses, the 22:15Z read and the `refused = blocked + fallback` check to the Source contract and the Cost bullet; name the manifest and safety tests as fixtures.
4. **Use one cohort for every command (L4).** `configurations_from_scores` should return the 29 cohort rows (or the commands should call the same function as `build_scores`), so the cross-check has one definition.
5. **Show the flag at the claim (L5).** A flagged winner of a bar or frontier result carries the flag in the printed result; the ranking tables stay as they are.
6. Not for this round: a stopping rule such as I56 proposed for the label mechanism no longer needs a counterpart. With the manifest and recommendations 1 and 2, a further finding on agent rows should be accepted only if it names a row that passes the capture filter and the manifest check.
