## 2. Methodology design recommendations

Prioritised. All use public data refreshed routinely.

1. **Make the passing cell the source of the route (closes L3, part of L4).** Add to each table row `reportDate`, `windowStated`, `upstreamSource`, `valuationBasis` (price list and date), `limitSchemaId`, `workloadId` and `recordRef` (stage file and row). When a cell passes, the build writes the route's `independentReports`, pooled value and observation dates from the cell and fails on any hand-entered difference, comparing report IDs and values and not the plan and model name. One pooled statistic: I recommend the median midpoint (it is what the cell publishes and it does not move when a second report is added at an extreme) with the monthly multiple 4.33·v ÷ fee for weekly cells; amend E33 in the same revision. Fixtures: a route whose reports differ from the cell's fails; 100/120 gives one value in the cell and the route; a pair with a shared upstream fails; a straddling report carries the E201a flag.
2. **Table integrity tests (closes L1).** For every row, the URL, observer, value and window must occur in the record (a one-page script suffices); every row of the stage-3 provider tables must be a row; a `notTabulated` block (observer, reason, record reference) lists the rest, so "every" is true by construction. Print the count of record reports, table rows and not-tabulated reports in the cell output.
3. **Publish a partition audit with the cells (closes the audit half of L4).** Per cell: each split applied (date or instant, basis), the current partition's start date and span in days, and the count of eligible, provisional and excluded reports per partition. Today the current partition began 2026-10-17T13:00Z for every Claude plan and 2026-10-24 for ChatGPT (four announcement splits in twelve days, with "28 days of shipping" still running), so "no cell passes" is partly structural: Claude Pro fails because its current partition holds one provisional report, and the pre-split $321 and $302 pair can never count; GPT-6 Astra on Pro $100 fails on count, because its 1.45× pair sits in an earlier partition. The published reasons differ from the closest-cell narrative in the O71 outcome; readers should see why.
4. **Rounding-aware concordance, published beside the whole-range test.** E270's whole-range rule penalises coarse meter readings rather than disagreement. With ranges [l_i, u_i], the whole-range test is max u ≤ 1.20·min l; a pair has a common reading within the margin iff max l ≤ 1.20·min u. Probe: two reports 7% apart (points 8.44 and 9.05) with whole-percent ranges [7.84, 9.04] and [8.40, 9.70] fail at 1.24× under the first rule and pass under the second (and pass as points). A provisional report with a wide range (K45SLE alone is 1.43×) can veto a cell it cannot help admit. Publish both ratios per cell and say which governs; E270 is an editor rule, and O74 (outliers) is untouched.
5. **Generate the remaining hand-typed Plan clauses (closes L5).** Add the top-row figure and a lint rule for "top row" and "rank 1" claims, as E265 did for counts.

Not repeated: I64 recommendation 4 (Terminal-Bench and AA-LCR narrow noise readings) is recorded in the ledger as not adopted; I have no new argument.
